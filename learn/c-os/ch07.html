C for OS · Chapter 7

Functions — call, arguments, return

What goes in. What comes back. Who waits. Then the OS-shaped calls: fork, wait, kill, a signal handler. No story. Trace every line.

Jump to practice

1. What a function is

A function is a named job. You write the job once. You call it when you need it. The computer jumps into that job, runs it, then comes back.

Every C program already has one function: main. That is “start here.” main can call other functions. Those can call more functions.

The rule

A call has three parts you must name out loud:

  1. Arguments — values that go in (copies, in normal C).
  2. Body — the work inside the function.
  3. Return — the value that comes back to the caller. Or nothing, if the type is void.

Who waits: the caller stops at the call line. It does not run the next line until the callee has returned. That is normal C. fork is the famous exception. We reach it later on this page.

2. A full small program

#include <stdio.h>

int add(int a, int b) {   /* callee: named job */
  return a + b;           /* value goes BACK */
}

int main(void) {          /* caller: start here */
  int s;
  s = add(2, 3);          /* 2 and 3 go IN. main WAITS. */
  printf("%d\n", s);      /* runs only after add returns */
  return 0;
}
Trace — say this out loud 
1. main starts. Box s exists, value unknown.
2. main calls add(2, 3).
   Copies: a gets 2. b gets 3. These are NEW boxes inside add.
3. main is waiting. It does not print yet.
4. add computes 2 + 3, then return 5.
   The 5 travels BACK to the call site.
5. s gets 5. add's boxes a and b are gone.
6. printf prints 5.
7. main returns 0 to the operating system.

3. What goes in (arguments)

The names in the round brackets of the definition are parameters: int a, int b. They are local boxes that live only while the function runs.

The values in the call are arguments: add(2, 3). C copies those values into the parameter boxes. This is pass by value.

If the caller has a box x = 2 and you call add(x, 3), add does not receive the box x. It receives a copy of the number 2. If add writes a = 100, x in main is still 2.

That is why a function cannot swap two ints in the caller if you only pass the ints. You would need the address of the boxes. That is Chapter 8. Here you must feel the copy.

void bump(int n) {
  n = n + 1;     /* changes the COPY only */
}

int main(void) {
  int x = 4;
  bump(x);
  /* x is still 4 */
  return 0;
}

4. What comes back (return)

return expression; does two things at once:

  1. It sends that value back to the caller.
  2. It ends the function. Lines after return in that function do not run.

The type before the function name is the type of the value that comes back: int add(...) must return an int.

void means “nothing comes back.” You still call the function. The caller still waits until the body finishes. There is just no value to store.

void hello(void) {
  printf("hi\n");
  /* no return value */
}

int main(void) {
  hello();          /* main waits. Nothing to assign. */
  printf("done\n");
  return 0;
}

A function returns one value. Not two ints at once. If you need two results, you later use pointers or a struct (Chapters 8 and 9). For the exam, first lock this: one return, one value, or void.

return 0; from main is a message to the OS: this program ended without error. Non-zero usually means failure. You will see that idea again with fork returning -1.

5. Who waits (normal C)

Draw a stack of paper in your head. The current function is the top sheet.

  • When A calls B, you put B’s sheet on top. A is underneath, frozen.
  • When B returns, you throw B’s sheet away. A continues on the next line.
  • If B calls C, C is on top. B waits. A still waits.

So “who waits?” has a short answer: the caller waits for the callee. Always, in this chapter, until we say fork.

Library functions are the same rule. When you call printf, main waits until printf has finished writing. When you call sleep(2), main waits about two seconds. Waiting is not special to OS calls. OS calls just wait for bigger work (a child to die, a lock, a signal).

6. Order, nested calls, prototypes

In printf("%d\n", add(2, add(1, 1))); the inner add(1, 1) runs first. It returns 2. Then add(2, 2) runs. It returns 4. Then printf runs. Inner call first. That is how you trace nested calls.

A prototype (declaration) tells the compiler the name, the argument types, and the return type, before you call the function:

int add(int a, int b);   /* prototype: promise */

int main(void) {
  printf("%d\n", add(2, 3));
  return 0;
}

int add(int a, int b) {  /* definition: the real body */
  return a + b;
}

Without a prototype (or a definition above the call), old C guesses wrong types. You will think the function is “broken.” It is not. The compiler was not told the truth. Headers (Chapter 10) are bags of prototypes: fork, wait, kill, pthread_mutex_lock.

7. Function you write vs function you only call

You write add. You only call printf. Both are functions. The difference is who wrote the body.

OS exam C is full of functions you call but did not write: fork, exec, wait, kill, signal, mmap, shm_open. They still take arguments, they still return, and the caller still waits — except where the man page says the call does something extra (two processes after fork, or the OS later calling your handler).

OS door — still C, not the OS story

You do not learn process theory here. You learn how these four look as C functions. After this chapter you can read a lab file without drowning.

8. fork — a call that returns twice

pid_t fork(void); — no arguments. Return type is a process id (treat it as an int for tracing).

Normal function: one call, one return, back to one caller.

fork: one call, then there are two processes. Each gets a return value.

  • In the child, fork returns 0.
  • In the parent, fork returns the child’s pid (a positive number), or -1 if it failed. Then there is no child.
pid_t r = fork();
if (r == 0) {
  /* this body runs in the CHILD */
} else if (r > 0) {
  /* this body runs in the PARENT. r is the child's pid */
} else {
  /* r == -1. fork failed. still only the parent */
}

Who waits? After a successful fork, neither waits for the other just because you called fork. Both continue. If you want the parent to wait, you must call another function: wait or waitpid.

That is the whole “who waits” trap for the exam: fork does not wait. wait waits.

9. wait — the caller really stops

pid_t wait(int *status); — the parent calls this. The parent is the caller. The parent waits until one child ends (or there is an error).

What goes in: a pointer to an int, or NULL if you do not need the status. Pointers are Chapter 8. For this chapter, remember: wait is a function. Arguments in. A pid comes back (the child that ended), or -1 on error.

Who waits: the parent, inside the wait call, until that child is done. The child does not call wait for the parent in the normal exam picture. The child runs, then ends. The parent is the one blocked in wait.

pid_t r = fork();
if (r == 0) {
  /* child work, then return/exit */
} else if (r > 0) {
  wait(NULL);   /* parent STOPS here until the child ends */
  /* parent continues only after the child is gone */
}

10. kill — a function that sends a signal

The name is a lie for beginners. kill does not always end a process. It is a function you call to send a signal to a pid.

Prototype idea: int kill(pid_t pid, int sig);

  • What goes in: who (pid) and which signal (sig, for example SIGUSR1 or SIGTERM).
  • What comes back: 0 if the signal was sent, -1 if it failed (bad pid, no permission).
  • Who waits: the caller of kill waits only until the kernel has queued / delivered the send. It does not wait until the other process has handled the signal. That other process may run its handler later.

SIGUSR1 is the lab signal: “user signal 1,” not “always die.” SIGTERM asks a process to end. SIGKILL forces end and cannot be caught. You do not need more signal names for this chapter.

11. A signal handler — a function you do not call

This is the second exception, after fork.

You write a function that matches a special shape:

void handler(int sig) {
  /* keep this tiny. often only set a flag */
}

You do not write handler(SIGUSR1) in main as the normal path. You register it:

signal(SIGUSR1, handler);
/*  what goes in: which signal, and the ADDRESS of your function
    what comes back: old handler, or error
    who waits: signal() itself returns quickly.
    later, when the signal arrives, the OS CALLS handler for you. */

So: handler is a function. Its argument is the signal number. Its return is void. The caller, when the signal happens, is the operating system, not main.

That is why we later write volatile int flag and only set the flag in the handler. main loops and looks at the flag. You will see the pointer chapter for volatile and for “address of a function.” For now: function pointer means “the paper that says where the function lives.” signal needs that paper so the OS knows which job to run.

#include <signal.h>

volatile int got = 0;

void handler(int sig) {
  (void)sig;     /* we received it; we may ignore the number */
  got = 1;       /* only this. no printf in the strict picture */
}

int main(void) {
  signal(SIGUSR1, handler);  /* register. we do not call handler here */
  /* wait until got becomes 1, then continue */
  return 0;
}

12. Picture of the four OS calls as functions

fork()     in: nothing
           back: 0 in child, pid in parent, -1 on fail
           wait?: no. two sides continue

wait()     in: pointer to status, or NULL
           back: pid of dead child, or -1
           wait?: YES. parent frozen until a child ends

kill()     in: pid, signal number
           back: 0 or -1
           wait?: only for the send, not for the handler

handler()  in: signal number (OS passes it)
           back: void
           who calls it?: the OS, after you registered it
                         with signal(sig, handler)
