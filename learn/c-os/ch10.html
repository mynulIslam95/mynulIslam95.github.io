Headers — #include and the linker

Missing toolkit → will not build. This is why lock and shm_open fail on the lab machine. Two steps: compile (headers) and link (libraries).

Jump to practice Ch9 structs

1. Two failures that look the same until you read the line

Students say “mutex does not work.” There are two different broken steps:

  1. Compile error: the compiler never heard of the name. Missing #include, or you spelled it wrong.
  2. Link error: the compiler knew the name (header was there), but the body of the function was not found. Missing -lpthread or -lrt.
The rule

A header is a bag of prototypes (Chapter 7): names, argument types, return types. It is not the machine code. The library (libpthread, librt) is the machine code. #include is for step 1. -l... is for step 2.

2. What #include actually does

#include <stdio.h> copies the text of that header into your file before compile. After that, the compiler knows printf.

Angle brackets <pthread.h> mean “system header.” Quotes "my.h" mean “a header next to your code.” Labs use angle brackets.

Include what you call. Do not include at random. The man page for each function lists the header. That is the exam habit: look at the prototype line.

3. The headers you need for this OS C

#include <stdio.h>      /* printf, perror */
#include <stdlib.h>     /* exit, malloc */
#include <unistd.h>     /* fork, exec, sleep, close */
#include <sys/wait.h>   /* wait, waitpid */
#include <signal.h>     /* signal, kill, SIGUSR1 */
#include <pthread.h>    /* mutex, threads, sem_t on some systems */
#include <fcntl.h>      /* O_RDWR, O_CREAT */
#include <sys/mman.h>   /* mmap, MAP_SHARED, shm_open on some systems */
#include <sys/stat.h>   /* mode 0600 */
#include <semaphore.h>  /* sem_open, sem_wait — POSIX named semaphore */

You do not memorise every constant. You memorise: wrong or missing header → unknown name at compile time.

/* typical compile error */
implicit declaration of function 'fork'
unknown type name 'pthread_mutex_t'
‘shm_open’ undeclared

Fix: include the header from the man page. Then rebuild.

4. The linker — where -lpthread and -lrt live

After the compiler accepts the file, the linker glues your .o to libraries.

printf lives in the C library. gcc links that by default. pthread_mutex_lock lives in libpthread. shm_open often lives in librt (real-time library) on Linux. Those are not default.

gcc lab.c -o lab -lpthread -lrt

-lpthread means “link libpthread.” -lrt means “link librt.” Order can matter on old gcc: put libraries after your .c file.

Typical link error (compile already succeeded):

undefined reference to `pthread_mutex_lock'
undefined reference to `shm_open'
undefined reference to `sem_open'

This is not a logic bug in your lock. The toolkit with the function body was not on the command line. Add -lpthread and/or -lrt. Then the program can build. Only then do races and deadlock become your problem.

5. Why lock fails (the two-layer checklist)

  1. Did you #include <pthread.h>? If not: unknown pthread_mutex_lock or pthread_mutex_t.
  2. Did you compile with -lpthread? If not: undefined reference to pthread_mutex_lock.
  3. Did you pass &m, not m? That is Chapter 8. It may compile (wrong types sometimes warn) and still be logically wrong.
  4. Did you init the mutex in the shared struct before lock? That is Chapter 9. It builds, then hangs or undefined.

Exam oral: say “header then library then pointer to the same mutex box.” That sentence scores. “I forgot the flag” is the same idea in lab language.

6. Why shm_open fails

  1. Missing #include <sys/mman.h> and often <fcntl.h>, <sys/stat.h> → undeclared at compile.
  2. Missing -lrt on Linux → undefined reference at link. (Some newer glibc put it in libc. The lab machine may still need -lrt. If the linker says undefined, add it.)
  3. Name must start with / on POSIX: "/myshm", not "myshm".
  4. Then ftruncate to sizeof(struct Block), then mmap with MAP_SHARED.

shm_open is a function (Chapter 7). It returns an int fd, or -1. It does not return the pointer. The pointer comes from mmap (Chapter 8). Students mix these two returns. Practice below hits that.

7. A lab file that can actually build

#include <stdio.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <unistd.h>
#include <pthread.h>

struct Block {
  pthread_mutex_t lock;
  int count;
};

int main(void) {
  int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0600);
  if (fd == -1) { perror("shm_open"); return 1; }
  ftruncate(fd, sizeof(struct Block));
  struct Block *b = mmap(NULL, sizeof(struct Block),
                         PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
  if (b == MAP_FAILED) { perror("mmap"); return 1; }
  /* init lock once, then lock / bump / unlock */
  return 0;
}

/* build:
   gcc lab.c -o lab -lpthread -lrt
*/

8. Your own header (one idea)

You may split a prototype into block.h and the body into block.c. The OS labs usually stay in one file. If you see #include "block.h", it is still Chapter 7 prototypes, just in another file. You still link all .c files together.

OS door

If the exam or lab asks why the program did not build, answer with the layer: compile (header) vs link (-lpthread/-lrt). If it built and still failed, that is pointers and who waits — not this chapter.
