pytest assertions

Write a test to verify an outcome repeatedly. When an assert condition is false, Python raises AssertionError. Pytest reports it as a test failure.

Run the code

def remaining(balance, expense):
    return balance - expense

actual = remaining(100, 12)
assert actual == 88
print("Check passed")

Output

Check passed

How it works

  1. The function returns 88.
  2. 88 == 88 is true, so the assertion passes.
  3. With an expected result of 87, the assertion raises AssertionError before the last print.
Common mistake

Use explicit validation or an exception for invalid production input. Python may disable assertions when it runs in optimized mode.

Install pytest in the environment from Type hints and dependencies. Derive expected answers from the requirement so your test does not copy the implementation’s bug.

Arrange Act Assert

Arrange the inputs, act by calling the target operation and assert the expected outcome. Keep setup simple so mistakes are easy to locate.

Run the code

def debit(balance, amount):
    return balance - amount

def test_valid_debit():
    opening = 100
    remaining = debit(opening, 12)
    assert remaining == 88

test_valid_debit()
print("Test passed")

Output

Test passed

How it works

  1. opening = 100 prepares the input.
  2. debit(opening, 12) operation under test।
  3. The assertion checks the result. The direct call runs this example as a standalone script.
Common mistake

Checking only that a function was called can miss a wrong result. Tests that mirror every internal call can break during harmless refactoring.

Pytest discovers test_valid_debit automatically. Test a pure business rule in isolation and cover database behavior with integration tests.

If debit adds the amount by mistake, where does the test fail?

Check your reasoning

The result becomes 112 and the assert line fails because it expects 88. Use the traceback and inputs to find the actual cause.

Edge cases and parametrization

For the rule above EUR 80, 80 is the exact boundary and 81 is just above it. Testing 100 alone cannot expose a mix-up between >= and >.

Run the code

def needs_review(amount):
    if amount < 0:
        raise ValueError("Negative amount")
    return amount > 80

cases = [(0, False), (80, False), (81, True)]
for amount, expected in cases:
    assert needs_review(amount) is expected
print("3 boundaries passed")

Output

3 boundaries passed

How it works

  1. The three inputs cover distinct cases under the rule.
  2. Tuple unpacking assigns each amount and expected result to separate names.
  3. Any wrong answer triggers an assertion failure. The script prints a summary when the checks pass.
Common mistake

Decide whether invalid negative input should return false or raise an exception. Assert the specific exception type so unrelated errors cannot satisfy the test.

The practice below shows parameterized tests. Select meaningful cases such as empty input, malformed input, the exact boundary and the adjacent value.

Try a change

How can pytest report each case separately?

Check your reasoning

@pytest.mark.parametrize("amount, expected", cases) lets pytest run each case separately in test_review(amount, expected). For ValueError, with pytest.raises(ValueError): checks the expected exception.

Tracebacks

Start with the smallest input that reproduces the reported balance error. Subtracting raw text can raise TypeError. The final traceback line gives the error type and the frames above show the call path.

Run the code

raw = "12"
print(type(raw).__name__)
amount = int(raw)
remaining = 100 - amount
print(remaining)

Output

str
88

How it works

  1. The raw input is a string, so the original 100 - raw expression fails.
  2. int(raw) converts the text to an integer.
  3. The subtraction now gives 88. The wrong type came from an earlier input boundary.
Common mistake

Verify what input format is allowed and how invalid text should be handled before adding a conversion.

Reproduce the bug, minimize the input, form a hypothesis, inspect the evidence, make one fix and add a regression test.

Logging without secrets

An import failed and its log only says error. Include safe details that help identify the request, count rejected rows and locate the failing stage.

Run the code

import logging
import sys

logging.basicConfig(level=logging.INFO, stream=sys.stdout, format="%(levelname)s %(message)s", force=True)
logger = logging.getLogger("tracker")
logger.info("import_complete request_id=%s rejected=%s", "demo-42", 2)

Output

INFO import_complete request_id=demo-42 rejected=2

How it works

  1. The application entry point configures logging.
  2. A named logger identifies which component emitted an event.
  3. Placeholders add a request ID and row count while keeping tokens and full records out of the log.
Common mistake

Keep passwords, raw tokens and full customer rows out of logs. Log each exception at a layer that can add useful context.

Use INFO for significant normal events, WARNING for recoverable concerns and ERROR for failed operations. Configure application logging once at the entry point.

Try a change

What would you log to link events from one import? Does that value prove authorization?

Check your reasoning

A correlation or request ID connects events. Authorization requires a trusted identity and policy check.

Where to start debugging

Make the test fail before fixing the bug. Make a small change, rerun it and check adjacent boundaries. For flaky tests, investigate shared state, timing and cleanup.

Practice 1: Catch the Threshold Bug

The code uses amount >= 8000 and the requirement says amount > 8000. Write a regression test, then fix the comparison.

Hint

Testing 9000 alone misses the exact boundary at 8000.

See Solution

Test the adjacent values 8000 and 8001.

Walk through the solution

The exact-boundary case catches the wrong >= comparison. The adjacent case checks that the first value above the boundary still requires review.

def requires_review(amount_cents):
    return amount_cents > 8000

def test_exact_threshold_is_not_reviewed():
    assert requires_review(8000) is False

def test_one_cent_over_threshold_is_reviewed():
    assert requires_review(8001) is True

test_exact_threshold_is_not_reviewed()
test_one_cent_over_threshold_is_reviewed()

Practice 2: Assert an Invalid-input Contract

Test that parse_amount("oops") raises ValueError and that a valid integer string returns an integer.

Hint

If invalid data returns 0, the caller could mistake it for a genuine zero.

See Solution

State the exception in the contract and check its type with pytest.raises.

Walk through the solution

pytest.raises fails when the code does not raise ValueError. The separate valid-input assertion catches an implementation that always raises an error.

import pytest

def parse_amount(raw):
    return int(raw)

def test_valid_integer():
    assert parse_amount("1250") == 1250

def test_malformed_amount():
    with pytest.raises(ValueError):
        parse_amount("oops")

Lab: Test a boundary and keep a token out of logs

A support report must count the exact limit as acceptable. Its log should include a request ID so an engineer can find the event. The token must stay out of the log. Save the file below as test_check.py. In a uv project, first run uv add --dev pytest.

Show the worked solution and verified output

test_check.py

import logging
import pytest

logger = logging.getLogger("fde.check")

def check_limit(count, limit, request_id, token):
    logger.info("request=%s count=%d", request_id, count)
    return count <= limit

@pytest.mark.parametrize("count, expected", [(9, True), (10, True), (11, False)])
def test_boundary_and_log(count, expected, caplog):
    token = "fixture-secret"
    with caplog.at_level(logging.INFO, logger="fde.check"):
        allowed = check_limit(count, 10, "req-42", token)
    assert allowed is expected
    assert "request=req-42" in caplog.text
    assert token not in caplog.text
Line-by-line explanation
  1. import logging

    Use Python’s logging tools.

  2. import pytest

    Use pytest to run multiple cases and capture logs.

  3. logger = logging.getLogger("fde.check")

    Give this component its own logger.

  4. def check_limit(count, limit, request_id, token):

    Define a small boundary rule with a sample credential.

  5. logger.info("request=%s count=%d", request_id, count)

    Log only the ID and count, leaving the token out.

  6. return count <= limit

    Accept counts at or below the limit.

  7. @pytest.mark.parametrize("count, expected", [(9, True), (10, True), (11, False)])

    Run the same test below, at and above the limit.

  8. def test_boundary_and_log(count, expected, caplog):

    Receive one input pair and pytest’s log capture fixture.

  9. token = "fixture-secret"

    Use harmless test text as a stand-in for an actual secret.

  10. with caplog.at_level(logging.INFO, logger="fde.check"):

    Capture the messages from this logger at INFO during the act step.

  11. allowed = check_limit(count, 10, "req-42", token)

    Call the rule with one test case.

  12. assert allowed is expected

    Check the returned Boolean.

  13. assert "request=req-42" in caplog.text

    Check that an engineer can locate the log.

  14. assert token not in caplog.text

    Fail if a future change leaks the token.
