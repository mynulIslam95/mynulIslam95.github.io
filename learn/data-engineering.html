CASE STUDY 01

A320 Quality Data Platform

Turn raw fictional aircraft-quality records into validated relational data and trustworthy reporting exports.

View actual source code ↗

System walkthrough, step by step

  1. Generate five synthetic datasets: 120 aircraft, 960 inspections, 365 findings, 314 corrective actions and 360 milestones.
  2. Inspect raw CSV schemas, IDs, dates, status values and parent-child references.
  3. Run pipeline checks for required values, duplicates, malformed dates, invalid statuses and orphan records.
  4. Load validated records into SQLite with linked tables and aircraft-level reporting view.
  5. Export quality summary CSV plus validation report for downstream use.
  6. Optionally load PostgreSQL with primary-key upserts. Treat this as an optional path until tested live.
  7. Optionally import Drive CSV into Google Sheets via Apps Script, generate a weekly report and configure a trigger.

Run it yourself

python -m src.generate_demo_data
python -m src.pipeline
python -m unittest discover -s tests -v

Files to inspect: src/generate_demo_data.py, src/pipeline.py, src/postgres_loader.py, data/raw/, data/processed/, google_apps_script/Code.gs, tests/

Interview questions and answers

Why five tables?

The entities have different grains and one-to-many relationships. Normalizing them reduces repeated fields and supports traceable joins.

How is quality enforced?

Before reporting, checks reject or report missing fields, duplicates, invalid statuses and broken foreign-key relationships.

Is the weekly job a streaming pipeline?

No. The Apps Script rereads a configured Drive CSV. Incremental ingestion and automated source-file replacement are not implemented.

What happens on a second PostgreSQL load?

The loader uses primary-key upserts to avoid simple duplicate inserts, but a real PostgreSQL integration test is still needed.

Honest boundary: Synthetic data only. No Skywise connection, no aircraft-release decisions. Live Google authorization and PostgreSQL integration are not yet confirmed.

CASE STUDY 02

A320 Quality Control Tower

Help a fictional quality team explore site-level indicators, investigate individual aircraft and track corrective actions.

View actual source code ↗

System walkthrough, step by step

  1. Launch the local Python HTTP backend and initialize synthetic SQLite records if needed.
  2. Serve HTML, CSS and JavaScript to the browser.
  3. Load summary metrics and site filters through HTTP requests.
  4. Open an aircraft investigation to inspect linked quality records.
  5. Update a finding or corrective-action status, then refresh the visible data.
  6. Log feature requests and assess whether the needed data is available.
  7. Export dashboard CSV; optionally let Google Apps Script read that CSV from Drive and rebuild Sheets reports.

Run it yourself

python -m app.backend
# open http://127.0.0.1:8501
python -m unittest discover -s tests -v

Files to inspect: app/backend.py, app/static/index.html, app/static/app.js, app/static/style.css, google_apps_script/Code.gs, tests/

Interview questions and answers

Is this Palantir Skywise?

No. It is an independent dashboard inspired by the exploration, application and reporting workflows associated with Contour, Workshop and Slate.

What is the update path?

A browser action calls the backend, which validates and updates SQLite, returns a response and lets the UI refresh its view.

How do you evaluate a feature request?

Identify the user question, required fields, source availability, data quality, API/UI changes, acceptance criteria and operational risk.

How is Google Sheets refreshed?

Apps Script imports a fixed Drive CSV, validates numeric fields and rebuilds summary tabs. A Monday trigger is optional. Live authorization remains untested.

Honest boundary: Local demo without authentication. Do not deploy publicly. Not connected to Skywise or real Airbus systems.

CASE STUDY 03

A320 Quality Intelligence RAG

Answer questions about fictional quality documents by retrieving supporting text, with optional Gemini-generated responses.

View actual source code ↗

System walkthrough, step by step

  1. Install FastAPI dependencies and launch the local app.
  2. On first startup, generate 120 synthetic aircraft documents.
  3. Index searchable document text in SQLite FTS5.
  4. Receive a question through the browser or /api/ask endpoint.
  5. Search for relevant documents using lexical full-text matching.
  6. Return evidence and source filenames when no Gemini key is configured.
  7. If GEMINI_API_KEY is configured, send retrieved context to Gemini for optional response generation.
  8. Return source references and label generated output cautiously; inspect retrieval and API tests.

Run it yourself

pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
python -m unittest discover -s tests -v

Files to inspect: app/main.py, requirements.txt, tests/, optional QUALITY_DB environment variable

Interview questions and answers

Is this vector RAG?

No. Retrieval uses SQLite FTS5 lexical search, not embeddings or a vector database.

Why return sources?

To make the retrieved evidence inspectable. Source names do not guarantee that every generated statement is correct.

What happens without Gemini?

The service returns retrieved evidence only, so it remains useful without an external API key.

How would you evaluate it?

Create a set of known questions and expected evidence, measure retrieval relevance and answer correctness separately, and test unsupported queries.

Honest boundary: Live Gemini calls are not confirmed. No authentication. Generated answers may be wrong and cannot support safety decisions.

05 / STUDY ROUTINE

14-day interview sprint

Days 1–3: Python, SQL and relational model. Write 10 queries and draw the five-table ERD.

Days 4–5: Run Project 1, inspect raw vs processed files, break validation deliberately and fix it.

Days 6–7: Run Project 2, trace a site KPI and status update, then explain Apps Script CSV refresh.

Days 8–9: Run Project 3, inspect retrieval-only output and explain FTS5 and Gemini boundaries.

Days 10–11: Review HTTP, tests, GitHub Actions, Linux, secrets and deployment security.

Days 12–13: Prepare prototype-demo story, feature feasibility analysis and 12 interview answers.

Day 14: Mock interview: explain all three projects from memory, then verify claims against the code.
