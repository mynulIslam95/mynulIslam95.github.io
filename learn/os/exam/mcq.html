Process, fork, exec, wait, kill

Story page: OS1

Q01

True or false. fork() gives every new process the ID of its parent.

No. The child gets 0. The parent gets the child’s PID. The child reads its parent with getppid().

Q02

True or false. fork() returns the ID of the new child. That is the whole truth.

No. Only the parent sees the child’s PID. The child sees 0. If fork() fails, the parent sees −1. The bare sentence is false.

Q03

True or false. After fork(), parent and child can read each other’s heap.

No. Each building has its own money box. The child gets a copy. A write in one heap does not show in the other. That is the point of a process versus a thread.

Q04

True or false. A child process never has two parents at the same time.

Yes. One parent. If that parent dies, init may adopt the child. Still one parent.

Q05

True or false. A parent may have only one child.

No. fork() as often as the limit allows. Two fork() calls in a row already make more than one child.

Q06

True or false. Two fork() calls in a row can make a process its own grandfather.

No. fork() only makes children. It never points back up. You get a tree, not a loop.

Q07

True or false. exec() starts an extra process next to the caller.

No. exec() replaces the program in the same process. Same PID. No new building. fork() is the one that copies the shop.

Q08

True or false. If a parent calls wait() or waitpid() on its children, those children do not stay zombies.

Yes. A zombie is an exited child whose exit code nobody collected. waitpid() collects it and the table entry goes away.

Q09

True or false. To avoid becoming a zombie, a process should call waitpid() before it itself ends.

No. The zombie is the dead child, not you. Your parent must wait for you. You wait for your own children.

Q10

True or false. kill() always sends SIGUSR1.

No. You pass the signal as an argument. The usual terminate signal is SIGTERM. SIGUSR1 is only one choice.

Q11

True or false. kill() can never end your own parent.

No. kill(getppid(), SIGKILL) is allowed if you have the right. There is no magic shield on the parent.

Q12

True or false. kill() can only terminate a process.

No. It sends a signal. That signal may stop, continue, or run a handler. Death is only the famous case.

Q13

True or false. A normal global variable cannot tell you, after fork(), whether you are parent or child.

Yes. The global is copied as the same number in both shops. The return value of fork() is what differs: child PID versus 0.

Q14

True or false. After fork() there is no variable at all that can tell parent from child.

No. The return value of fork() is that variable. if (fork() == 0) is the child.

Threads and the CPU

Story page: OS2

Q15

True or false. The OS protects one thread’s address space from every other thread.

No. Threads of one process share the same address space. Isolation is per process, not per thread.

Q16

True or false. Multithreading is useless on a machine with only one CPU.

No. While one thread waits for the disk, another thread can use the core. Overlap still helps.

Q17

True or false. On a 4-core CPU, at most 4 threads can be in the RUNNING state at once.

Yes. RUNNING means “on a core right now.” Extra threads are READY, waiting for a core.

Q18

True or false. The OS may suspend one thread to free main memory.

No. Swap for memory is a whole-process job. One thread still sits in the same address space as its siblings.

Signals and timers

Story page: OS8

Q19

True or false. A program may register a handler for SIGUSR2.

Yes. SIGUSR1 and SIGUSR2 are for you. SIGKILL is the one you cannot catch.

Q20

True or false. After a signal() handler finishes, the program continues where it was interrupted.

Yes. That is the point of a handler. A blocking call may then return EINTR, but you do not jump to main().

Q21

True or false. After a signal() handler finishes, the program continues at the start of main().

No. That would restart the whole program. Control goes back to the interrupted instruction.

Q22

True or false. Linux delivers ordinary signals in FIFO order.

No. Ordinary signals do not even queue a second copy of the same signal. There is no FIFO promise.

Q23

True or false. A Linux timer can only wake you with a signal. It cannot start a thread.

No. POSIX timer_create can fire a signal, or it can start a callback thread (SIGEV_THREAD).

Q24

True or false. Linux timers always start a new thread.

No. Often they only send a signal. A new thread is optional, not the default story.

Locks, deadlock, watchdog

Story page: OS3 / OS5

Q25

True or false. Mutexes avoid deadlocks among threads.

No. A mutex stops a race on one key. Two threads can still each hold one key and wait for the other. That is deadlock.

Q26

True or false. A watchdog program prevents deadlocks.

No. A watchdog notices a stall after it has already happened. The deadlock still occurred.

Q27

True or false. A watchdog should be a separate process from the thing it watches.

Yes. If it lives in the same process, the same crash can kill the watcher too.

Q28

True or false. A semaphore can count something.

Yes. A counting semaphore is a number: how many violins are still free.

Q29

True or false. Shared memory is a synchronisation tool.

No. It is a window both shops can see. It does not take turns. You still need a mutex or a semaphore beside it.

Pipes, files, network words

Story page: OS1 / OS8

Q30

True or false. Bytes in a pipe come out in FIFO order. You cannot reorder them.

Yes. A pipe is a kernel queue. First byte in is first byte out.

Q31

True or false. accept() is how a server takes a client’s connection.

Yes. The listening socket stays. accept() returns a new socket for that one client.

Q32

True or false. File bits d-r-r---- mean a directory full of runnable programs.

No. d is a directory, but there is no x, so you cannot even enter it. Whether files inside can run is their own bits, not these.

Q33

True or false. UNIX treats many things as a file.

Yes. Disk files, devices, pipes, sockets: open, read, write, close.

Q34

True or false. If an IP packet is lost, a higher layer can still repair the loss.

Yes. IP does not retry. TCP above it can ACK and send again.

Hardware, cache, time

Story page: OS10

Q35

True or false. DMA reduces how much work the CPU must do for a copy.

Yes. The device writes memory itself. The CPU is free for other work during the transfer.

Q36

True or false. The user program controls the switch from kernel mode back to user mode.

No. The kernel and the hardware do that (return from trap or interrupt). User code cannot promote itself.

Q37

True or false. Virtual memory lets a process use more memory than the machine physically has.

Yes. Unused pages sit on disk. That is paging.

Q38

True or false. A good cache should use the smallest possible block size.

No. Tiny blocks miss more often. Block size is a trade, not “as small as you can”.

Q39

True or false. Caching always makes the system slower.

No. A cache is there to make the average case faster. It only hurts in rare bad patterns.

Q40

True or false. A timer event executes a trap.

No. A timer is an interrupt from outside, asynchronous. A trap is a synchronous event from the running instruction, like a syscall.

Q41

True or false. Blocking system calls belong inside interrupt handlers.

No. A handler must finish fast. Blocking there can freeze the machine. Blocking waits belong in process context.

Windows

Story page: OS9

Q42

True or false. WaitForMultipleObjects() always waits until every object is signalled.

No. Only if you pass “wait for all”. Otherwise it returns when any one object is signalled.

Q43

True or false. Windows 10 window handling is event-driven.

Yes. GetMessage / DispatchMessage. The window procedure runs when a message arrives.

Q44

True or false. The Windows 10 shell is an 8-bit MS-DOS environment.

No. cmd.exe is a normal Win32 program. DOS is only old compatibility.

Q45

True or false. The window callback runs again and again inside the main message loop, as the loop body.

No. The loop runs again and again. For each message it calls the window procedure once, then comes back.

Q46

True or false. After WM_QUIT, GetMessage() returns TRUE.

No. It returns 0. That is how while (GetMessage(...)) stops.

Q47

True or false. A Windows mutex is a synchronisation object.

Yes. CreateMutex gives a waitable kernel handle. That is not the same as “mutexes stop deadlock”.

Q48

True or false. Unnamed Windows sync objects are how two processes wait on each other.

No. With no name, the other process cannot find the handle. Unnamed is for threads in one process, unless you duplicate the handle.

Q49

True or false. A Windows event can synchronise threads that live in different processes.

Yes. Give the event a name, or duplicate the handle. Then both processes wait on the same kernel object.

Q50

True or false. In Windows, file mapping and memory mapping are almost the same call path.

Yes. Both use CreateFileMapping and MapViewOfFile. Only the backing store differs.

What an OS is

Story pages: OS10 · OS11 · OS0 is the short door

Q51

True or false. A microkernel often pays extra context switches, so it can be slower.

Yes. Drivers and servers sit in user space. Each ask is an extra IPC hop.

Q52

True or false. Concurrent jobs always run at the same instant.

No. Concurrent means their lives overlap. On one core they take turns. Parallel means same instant.

Q53

True or false. A process is an instance of a running program.

Yes. The file on disk is the program. The running copy with its own memory is the process.

Q54

True or false. The stack stores parameters and return addresses.

Yes. Each call pushes a frame: where to return, and the arguments.

Q55

True or false. The stack is part of the PCB.

No. The PCB is the kernel’s card about the process. It may hold a pointer to the stack. The stack itself lives in the process memory.

Q56

True or false. A plug-and-play OS boots faster.

No. Plug-and-play spends time finding and setting devices. It is convenience, not a shorter boot.
