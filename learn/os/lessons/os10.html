1. What the OS is

The laptop is rooms: a worker (CPU), a table (RAM), a store (disk), doors to the street (keyboard, network, screen). The rooms do not know Chrome.

The operating system does two jobs at once. From the top, it is an easier machine: a program opens a named file instead of talking to the disk chip. From the bottom, it is a resource manager: it plans processes, memory, files and devices, and it stops one guest from taking another guest’s table.

The kernel is the part with the keys. A desktop picture is not the kernel. A system can run with no GUI and still be an OS.

Twist

True or false. If the CPU already executes instructions, we do not need an OS.

No. The CPU runs lines. The OS decides who runs, who may touch memory, and how a device request is handled. A tiny embedded loop can live without a general OS. A laptop with Chrome cannot.

True or false. Windows Explorer / the graphical desktop is the whole operating system.

No. That is a user interface. The kernel still manages CPU, memory, files and devices if the desktop is gone.

True or false. “Manage processes and files, and be the programs that start and control other programs” is a fair exam sentence for what an OS is.

Yes. That is the DIN idea on the Motivation slides: resource manager, and the basis that starts and controls other programs.

2. Four pieces of the computer

Lecture 03 starts with four boxes, not with Linux commands.

  1. Processor — runs instructions. Old name: CPU. Often sold by GHz.
  2. Main memory — holds the program and data that are in use now. Not permanent. Today we count it in GB.
  3. I/O modules — move data between the computer and the outside (disk, net, keys, screen).
  4. System bus — the road between processor, memory and I/O.

A new exam story can name a keyboard, a disk, or a timer. You still point at these four, plus devices the OS must manage (CPU time, RAM, disk, network, printer, timer).

Short (Westerkamp shape). Name at least four hardware resources an OS typically controls.

CPU, main memory, disk/storage, I/O devices (network, keyboard, printer), timer, bus. Four of those is enough. Chrome is not a hardware resource.

Twist

True or false. Main memory keeps your files after you pull the power plug.

No. RAM is not permanent. The store room is disk or SSD. That is why the hierarchy has a slower, lasting level.

3. Registers — tiny boxes in the worker

Registers sit inside the processor. Fast. Small. Not RAM.

  • PC — program counter. Paper to the place of the next instruction in memory.
  • IR — instruction register. Holds the instruction we are decoding or running now.
  • MAR — memory address register. Paper to a data place in memory.
  • MBR — memory buffer register. The bytes going to memory or coming back. Sometimes called MDR.
  • PSW / flags — ZERO, overflow, and a KERNEL bit: are we in kernel mode?

User-visible registers: a compiled program uses them so it does not walk to RAM for every add. Control/status registers: ordinary user code does not own them. Privileged OS code does.

The lecture’s cycle text once mixes PC and IR. For the exam use the table: PC = where next, IR = what instruction.

Twist

True or false. The program counter holds the instruction itself.

No. PC is an address. IR holds the instruction. Room number versus the person in the room. Same idea as a C pointer versus the int in the box.

True or false. Control and status registers are for kernel / control mode, not for ordinary machine code.

Yes. Lecture 03: they are usually not visible to ordinary machine code. The KERNEL flag lives here.

4. One instruction

A simple cycle: fetch (use PC, load into IR), decode, execute, then go to the next PC, or a jump, or an interrupt.

An instruction has an opcode (what to do) and often an address / operand (where the data is). Four families: move memory, move I/O, arithmetic/logic, change the flow (jump).

Worked numbers from the slide: memory 940 holds 3, memory 941 holds 2. LOAD 940, ADD 941, STORE 941. After that, 940 is still 3. 941 is 5.

Pipelines overlap parts of different instructions. Not every instruction is one clock.

Twist

True or false. After LOAD A; ADD B; STORE B, A holds the sum.

No. STORE writes the sum to B. A is only read. Change A and B in a new question: same rule, new numbers.

True or false. Every instruction takes exactly one clock cycle.

No. Time depends on the instruction and the chip. A pipeline can overlap fetch of the next with execute of this one.

5. User mode, kernel, privileged

Guests run in user mode: restricted. The kernel runs in kernel mode: more keys. Hardware helps stop a guest from talking to the disk chip itself.

A system call is a controlled ask. It is not every C function. Some library functions enter the kernel. Some do not.

A mode switch is a change of privilege. It is not automatically a process switch. The kernel may do the work and return to the same process.

A privileged instruction must not run in user mode. Examples: halt the CPU, load the page table, clear interrupt-enable, talk to an I/O port. If a user program could halt the CPU or turn the timer off, it could steal the shop.

Twist

True or false. The user program controls the switch from kernel mode back to user mode.

No. Hardware plus kernel (return from trap or interrupt). User code cannot promote itself.

True or false. Every system call switches to a different process.

No. Often the same process continues after the kernel returns. If the call blocks, another process may run. That is a later story (OS1).

Short (Westerkamp 2021, privileged instruction). Name one privileged instruction, and in a few words say why it must be privileged.

Example: HALT — a user could stop the CPU for everyone. Or CLI — turn the timer off and never give the CPU back. Or load CR3 / page table — map anyone’s memory. Or IN/OUT to a device port. One name plus that story is the mark.

6. Interrupt: pause, handle, resume

You read a book. The doorbell rings. You mark the page, open the door, then come back. That mark is saving the PC and PSW.

Four families on the slide:

  • Program — this instruction went wrong: divide by zero, illegal opcode, overflow, touch memory you do not own. Synchronous. Many people say trap / exception.
  • Timer — a clock inside the processor. Lets the OS run on a regular beat. Asynchronous. Not a trap.
  • I/O — a controller says “done” or “error”.
  • Hardware failure — power, parity.

Hardware job, in order: device signals → CPU finishes the current instruction → ack, device drops the line → push PC and PSW → jump to a handler (fixed, or per interrupt, or per device).

Software job: save the rest of the registers → talk to the device → restore registers → restore PC and PSW.

The program does not restart from line 1. An interrupt does not by itself mean “run a different process.” The OS may resume the same one.

A handler must be short. Do not sleep, do not take a mutex, do not printf. Set a flag. That is also C-for-OS P3.

Twist

True or false. A timer event executes a trap.

No. The timer is an interrupt from outside the current instruction. A trap is synchronous: this line caused it (syscall, fault). New wording, same split.

True or false. Blocking system calls belong inside interrupt handlers.

No. The handler must finish. Blocking there can freeze the machine. Wait in process context. Motivation slide: do not change the shared object in the ISR, or disable interrupts for a very short time — not a mutex.

True or false. Before the handler runs, the processor finishes the current instruction and saves PC and PSW.

Yes. Lecture 03 interrupt processing, steps 2 and 4. If he asks “list the actions,” start there, then software save of the other registers.

Short (Westerkamp 2021, interrupts). Give one example where an interrupt makes sense, and say why (not polling).

Disk or network done: I/O is slow. Without an interrupt the CPU would sit in a check-loop. With an interrupt the CPU works on another program, the controller rings, PC/PSW are saved, the ISR runs, then we resume or schedule. Keyboard is also fine. “Makes sense” = CPU can use the wait time.

7. A second interrupt arrives

Ask two facts first: is that interrupt enabled? Does its priority beat the handler that is already running?

Sequential: finish this ISR, then take the next. Simple. Urgent work can wait.

Nested / priority: a higher-priority interrupt may interrupt a lower ISR. Faster for urgent work. More stacks to save.

Do not disable interrupts for a long time. And: masking interrupts on this CPU does not stop another CPU from touching the same bytes. That needs a lock across CPUs — later page OS3.

Twist

True or false. If an interrupt hits during an ISR, the new event is always lost.

No. It may wait (sequential) or nest (higher priority, enabled). You need those two facts. Guessing “lost” is the fail.

True or false. Disabling interrupts on one CPU protects a shared variable from every other CPU.

No. The other core can still write. Cross-CPU needs a real lock. This is the twist he can add to a “just disable interrupts” answer.

8. Memory ladder and locality

You cannot have fast, huge, and cheap in one technology. So we stack:

registers → CPU cache → RAM → SSD/disk.

Down the ladder: cheaper per bit, bigger, slower, used less often (if the program is kind).

Temporal locality: you will touch this again soon (a loop counter). Spatial locality: you will touch the neighbour (the next array cell). A cache line is a block of neighbours, not one byte.

A cache hit is not a page fault. Paging is virtual memory, later. A cache does not make RAM permanently larger. It holds copies.

Twist

True or false. A cache hit is the same as a page fault.

No. Hit = found in this cache. Page fault = virtual memory / not in RAM (or protection). New question can mix the words. Keep them apart.

True or false. Virtual memory lets a process use more memory than the machine physically has in RAM.

Yes. Unused pages can sit on disk. That is paging. Do not mix it with “the L1 cache grew.”

9. Cache — the calculation room

Faster than RAM, slower than registers. The programmer and the OS usually do not see it. Dedicated hardware walks the tags: is this block in a line?

On a miss, a whole line / block comes in. If the cache is full, a line leaves. LRU is the standard replacement on the slide. Mapping can be “only one legal line” or “any line.”

Write-through: write RAM now as well. Write-back: mark dirty, write RAM later (on replace). Problem of write-back: RAM can be stale; I/O / DMA / other CPUs must see the truth or you need extra rules.

Lecture numbers: first level 0.1 µs, second 1 µs extra, hit ratio 95%.

Average = 0.95 × 0.1 + 0.05 × (0.1 + 1) = 0.15 µs.

If he gives a total miss time already including the cache check, do not add 0.1 twice.

Larger blocks help spatial locality — until you have too few lines and thrash. “Smallest possible block” is false.

Short. Hit 95%, cache check 0.1 µs, extra memory 1 µs. Average access time in µs? Number only is enough.

0.15 µs. He can change 95% to 80%: then 0.1 + 0.20×1 = 0.30 µs. Same formula, new number. That is a new question you still own.

Twist

True or false. A good cache should use the smallest possible block size.

No. Hit ratio often rises with block size because of spatial locality, then falls when you have too few lines. It is a trade, not “as small as you can.”

True or false. Caching always makes the system slower.

No. The point is a faster average. A rare bad pattern can hurt. Do not write “always.”

True or false. The OS picks, in software, which L1 cache line to replace on every miss.

No. Lecture: cache is not visible to the programmer nor to the OS; dedicated hardware. The OS does pages in RAM vs disk. Different ladder step.

Westerkamp SS2021 · 18 points · cache loop

One CPU, one process, cache 1 MiB, line 64 bytes. Array of 64-byte blocks, loop i from 0 to 0x4000−1, always block[i][0]. FIFO vs LRU vs Random: who has the highest hit rate, on average? Why?

Solution steps — do this, do not quote a slogan
  1. 0x4000 = 16384 iterations. Each iteration touches one 64-byte block. Working set = 16384 × 64 B = 1 048 576 B = 1 MiB.
  2. That equals the cache size. After the first cold pass, the cache can hold exactly the loop.
  3. Next passes: FIFO and LRU keep that set → hits. Random is not better; it is not systematically worse only if no further misses occur. The mark is: the working set fits, so replacement barely matters after warmup.
  4. If he changes the loop to 2 MiB, the set no longer fits. Then LRU usually beats FIFO on a tight loop, and Random is noisy. Same machine, new size. Compute first.

10. Three ways to do I/O

Ask two questions: How do we know the device is ready? and Who copies the bytes?

  • Programmed I/O / polling: CPU checks status again and again, then CPU copies. Control / status / transfer commands. Burns CPU. Fine if the wait is tiny.
  • Interrupt-driven: device rings. No busy wait. Still the CPU usually copies each byte in the simple model. Extra cost: interrupt overhead.
  • DMA: CPU tells a DMA box: read or write, which device, start address in RAM, how many words. Then the DMA box copies. CPU is out of the copy loop. Finish often still an interrupt. You still need a DMA module. CPU is not “doing nothing forever” — it sets up and it finishes.

True or false. DMA reduces how much work the CPU must do for the copy itself.

Yes. The device/DMA writes memory. The CPU is free during that copy. Setup and completion still exist.

Twist

True or false. DMA means the CPU never talks to that transfer at all.

No. The CPU/OS sends direction, device, start address, size. Then it is out of the byte loop. A new question can hide that setup list. Recite the four fields.

True or false. Polling is always the wrong design.

No. A very short wait can be cheaper than an interrupt. The trade is CPU time versus delay versus interrupt cost.

11. Resources: share, steal, clash

Motivation bottom-up, and the SS2018 six short prompts, live here. Details of mutex code are OS3. Deadlock and priority inversion are OS5. You still must classify a resource on this page.

  • Many at once, no problem: a read-only file.
  • Must not be concurrent: a counter x = x + 1 with no lock (lost update).
  • Easy to take away (preemptible): the CPU.
  • Cannot safely take away: a mutex held in the middle, or a printer mid-page.
  • Two tools that keep consistency: mutex and semaphore.

Even a file you can share should sometimes be exclusive — if someone writes. Concurrent does not mean “same instant.” On one core, lives overlap and take turns. Parallel is same instant (more cores).

History you need as why, not as lawsuits: one job at a time wasted the CPU on I/O wait → multiprogramming keeps another job ready → time sharing gives short slices so a human can type. Three OS aims on the overview: convenience, efficiency, ability to evolve.

Twist

True or false. Concurrent jobs always run at the same instant.

No. Concurrent = lives overlap. On one core they take turns. Parallel = same instant. Motivation definition of concurrency: no well-defined predecessor-successor.

True or false. The CPU is a resource the OS can take away from a thread at an instruction boundary.

Yes. Preemptible. A held lock or a printer mid-page is the opposite. SS2018 task 1 uses this split.

True or false. A process is an instance of a running program.

Yes. File on disk = program. Running copy with its own memory = process. Two Word windows: still one program file. Full fork story is OS1.

Short (Westerkamp, process switch — hardware half). Name at least three incidents that can cause a process switch.

Timer interrupt (time slice). I/O interrupt (disk done, wake someone). Trap / system call / fault. Blocking wait. Yield. The first three are this page. Blocking wait is OS1. A new question may mix them. List what the story actually contains.

SS2018 task 1 · six resource prompts

Shareable? Must not share? Preemptible? Not preemptible? Inconsistency example? Two consistency tools?

Solution steps
  1. Shareable: read-only file or table.
  2. Must not share: x = x + 1 with no lock.
  3. Preemptible: CPU.
  4. Not: held mutex, or printer mid-page.
  5. Inconsistency: two threads read a balance, both add, both write — one add lost.
  6. Tools: mutex and semaphore. How they work: OS3.

Gräßner T/F · hardware family (also Floor 3)

DMA reduces CPU copy work? User program returns itself to user mode? Virtual memory bigger than RAM? Smallest cache block is best? Cache always slower? Timer is a trap? Blocking calls inside an ISR?

Solution steps
  1. DMA yes. User cannot promote itself: false. Virtual memory yes.
  2. Smallest block: false. Cache always slower: false. Timer = trap: false. Block in ISR: false.

Gräßner T/F · what an OS is

Microkernel extra switches, can be slower? Concurrent means same instant? Process = running instance?

Solution steps
  1. Microkernel: often yes, extra IPC. Concurrent: false for “same instant.” Process: true.
