How an OS grew

Lecture 04, operating system overview. He is not required to repeat last year’s sentence. He can tell a new story about the same growth: why we have an OS, what it must do, and why serial jobs became batch, then several jobs in memory, then short slices for humans. Each room: the machine, then a twist, then True/False. Old papers sit at the end as traps. Registers, interrupt, cache, DMA are OS10. Fork is OS1.

OS0 is the five-minute door. This page is 100/100 on this family. C without stories: C for OS.

1. Three aims

The lecture opens with three jobs an OS must do, not with Linux commands.

  1. Convenience. A program opens a named file. You do not talk to the disk chip.
  2. Efficiency. CPU, memory, disk and devices are shared. One guest must not waste the whole shop.
  3. Ability to evolve. New hardware and new services can arrive without stopping the rest. You test a new piece without breaking the old service.

A new exam story can say “USB stick that did not exist when the laptop was bought” or “a nicer file window.” You still point at these three.

Short. Name the three OS objectives from the overview lecture.

Convenience. Efficiency. Ability to evolve. A new paper may use “easy to use”, “use resources well”, “grow without breaking service.” Same three.

Twist

True or false. If the OS is convenient, it does not need to be efficient.

No. The slide lists all three. A nice file name that wastes the CPU for every other program fails the second aim.

True or false. “Ability to evolve” means you can add a new function, test it, and put it in, without stopping the whole service.

Yes. That is the third bullet: development, testing, and introduction of new system functions without interfering with service.

2. Three views of the same machine

The computer is a stack of layers. Who you are changes what you are allowed to see.

  • End user. Wants the application. Does not want the chip.
  • Programmer. Wants the whole computer as a clean machine: open, read, write. Does not want the disk geometry, which may change next year.
  • OS designer. Sees everything. Job: give service to the other two.

Windows Explorer is a utility for the end user. It is not the kernel. The kernel still runs if the window is gone. That trap already lives on OS10.

Twist

True or false. The programmer should write sector numbers for every disk, so the program is faster.

No. The OS hides that. Hardware changes. The programmer uses a uniform read and write. Convenience plus ability to evolve.

True or false. The OS designer’s job is to provide service to the end user and to the programmer.

Yes. The designer sees the whole machine. The other two must not be annoyed by the internal details.

3. Services: start a program, hide a device, hide a file

The slide “Services provided by an OS (I)” is a list you can unpack in any new story.

  • Program development — editors, debuggers. These are utility programs, not the kernel itself.
  • Program execution — the OS initialises, suspends, schedules, and terminates programs.
  • Access to I/O devices — a uniform interface. The programmer does simple reads and writes. The chip stays hidden.
  • Controlled access to files — how bits sit on this disk is hidden. Who may open the file is not hidden: the OS checks.
  • System access — who may use the machine at all, and who may use this printer. Conflicts get a decision, not a crash.

Short. Name at least four services an OS typically provides.

Program development, program execution, I/O access, files, system access, error handling, accounting. Four of those is enough. Word is an application, not an OS service name.

Twist

True or false. The editor and the debugger are the kernel.

No. The slide says they are utility programs. The OS makes them easy to run. They are not the part with the keys.

True or false. File layout on disk can differ by device, and the OS still offers one open/read/write story to the programmer.

Yes. “Depends on the nature of the device. This is hidden to the user.” Plus protection on who may touch the file.

4. Services: errors and accounting

Two more lines on the second service slide. They look boring. Oral exams like them because they are not “fork.”

Error detection and response. Hardware: memory error, device dead. Software: divide by zero, touch memory you must not touch. The OS must react in a way that matches the error — stop that program, retry the disk, tell the log — not freeze the whole machine every time.

Accounting. Count who used what. Watch performance. Sometimes used for billing. Even if nobody is billed, the OS still needs numbers: who held the CPU, who filled the disk.

True or false. Divide by zero is a software failure the OS should handle.

Yes. The slide lists software failures: division by zero, forbidden memory. Hardware failures are listed too: memory error, device malfunction.

Twist

True or false. Accounting exists only so the university can send you an invoice.

No. The slide says statistics of usage and performance. Billing is one possible use, not the only one. A timer interrupt that counts slices is this family — details of the doorbell are OS10.

5. The OS is an odd manager

The OS manages CPU, memory, files, devices. Then the slide says something that sounds wrong until you sit with it:

  1. The OS is itself a program (or a suite of programs) that the processor executes. It is not a second computer sitting beside the CPU.
  2. It often gives up control. A user program then runs. The OS must depend on the processor to give control back.

How does it get the keys back? A timer interrupt, an I/O interrupt, a trap from a system call. That hardware story is OS10. Here you only need the odd fact: a manager that is also a guest of the same CPU.

Short. The OS gave the CPU to a user program. Name one way it can regain control.

Timer interrupt (time slice). I/O interrupt. Trap / system call / exception. Without a doorbell, a looping program never returns the keys. OS10 is the doorbell. This page is why the manager is odd.

Twist

True or false. The OS is a separate processor that watches the main CPU from the outside.

No. “It functions in the same way as ordinary computer software; it is a program executed by the processor.” There is no second brain. That is why interrupts matter.

True or false. After the OS starts a user program, it may have no CPU until an interrupt or a trap comes back.

Yes. It relinquishes control and must depend on the processor to allow it to regain control.

6. Why a live OS must change

A major OS lives for years. Three reasons it cannot stay frozen:

  • Hardware upgrades, new types of hardware. You keep a computer five years. Then you plug in a device that did not exist on the day you bought it. The OS must cope.
  • New services. The lecture’s example: Windows Explorer as a later utility, not as “the OS was always a desktop.”
  • Fixes. “Any OS has faults.” If you never update, it stays open to old holes.

This is the third aim (evolve) with stories attached. A new exam can change the device name. The reason stays.

Twist

True or false. If the laptop is five years old, the OS never needs a new device driver, because the hardware is finished.

No. The slide’s example is a peripheral invented after you bought the machine. The OS must evolve.

True or false. Leaving an OS unpatched because “it works” fights the lecture’s reason called fixes.

Yes. Faults stay. An OS that is never updated is vulnerable. Convenience of “do not touch it” is not the third aim.

7. Serial processing — no OS yet

ENIAC-class machines had nothing you would call an OS. A human owned a time slot. Two wastes:

  • Scheduling. You booked one hour. The job finished in twenty minutes, or it overran. Either way, the machine sat wrong.
  • Setup time. Load compiler, load program, save, load again, link. Each step: mount a tape, pull cards, put them back.

Pictures of Zuse Z1 and ENIAC on the slides are history. The exam wants the two wastes, not the year 1936.

Short. Name the two major problems of serial processing (no OS).

Scheduling (fixed slots, jobs early or late). Setup time (mount compiler, program, tapes, cards). A new story may say “USB stick” instead of tape. Point at setup waste.

Twist

True or false. ENIAC already had a kernel that scheduled jobs overnight.

No. “The earliest computers had nothing that could be called OS.” Humans ran the slot. Batch comes next.

8. Simple batch — a monitor runs the queue

To kill setup waste, the first OS was a monitor that ran a sequence of programs automatically. Jobs sat on cards or tape in a row — a batch. IBM 7090, early 1960s, IBSYS is the named example. You do not need the product name in every answer. You need the idea.

The monitor starts a job. When the job ends, it must branch back to the monitor. The monitor starts the next job.

Lessons learned, still true on a laptop:

  • Memory protection — a job must not write the monitor.
  • Timeouts — a looping job must not sit forever. That needs a timer.
  • Different modes — user job vs monitor. Privileged instructions stay with the OS. OS10 names those instructions.

True or false. In a simple batch system, a finished user program must return to the monitor so the next job can start.

Yes. “When the user program terminates it had to branch back to the monitor. The latter started the next program.”

Short. Simple batch taught three needs. Name at least two.

Memory protection. Timeouts (timer). Different modes (user vs monitor). A new wording may say “kernel mode.” Same lesson.

Twist

True or false. Simple batch already keeps a second job running while the first job waits for the printer.

No. Simple batch is one job after another. While that job waits for I/O, the CPU can sit idle. Several jobs in memory is the next room.

9. Multiprogrammed batch — do not idle on I/O

I/O devices were already much slower than the processor. Simple batch raised utilisation by removing human setup. Then people measured: while job A waits for disk or printer, the CPU is empty.

Multiprogramming (the slide also says multitasking) needs enough RAM for several programs at once. When A waits, run B. When the disk finishes, A is ready again. The scheduler chooses.

Goal of this step: processor utilisation. Not yet “a student typing at a terminal.”

You still need protection and scheduling. Two programs in RAM can destroy each other if they share with no rules. Mutex is OS3. Here you only classify the invention: another ready job while one waits.

True or false. Multiprogramming needs enough main memory to hold more than one program.

Yes. “Provided that the main memory was sufficiently large to store several programs.”

Twist

True or false. On one core, two multiprogrammed jobs always execute their instructions in the same instant.

No. One core, one instruction stream at a time. Lives overlap; they take turns. Parallel same-instant needs more cores. OS10 already used this split. The overview lecture is why they overlap: A waits for I/O, B runs.

True or false. The main reason for multiprogrammed batch was to use the CPU while another job waited for slow I/O.

Yes. Simple batch still wasted the processor on I/O wait. Several jobs in memory fix that. Interactive typing is the next room, not this one.

10. Time sharing — short slices for humans

Multiprogrammed batch maximised the processor. Then many people shared one computer through terminals. Utilisation is no longer the only issue. A human who types must get an answer soon.

Time sharing gives each user a short time slice. From her seat, it feels like a machine of speed about 1/n, where n is the number of users (ignore OS overhead).

Named early system: CTSS (Compatible Time-Sharing System), early 1960s, IBM 7094, up to 32 users. The name is useful. The idea is required: slices, response, many humans.

Extra lessons, on top of batch:

  • Memory protection, now also between users.
  • Resource allocation.
  • Mutual exclusive access to devices — two users must not print through each other.

The timer that cuts a slice is OS10. Mutex for a device is OS3. Here you name why those tools appeared.

Twist

True or false. Time sharing was invented only to raise CPU utilisation above multiprogrammed batch.

No. Batch already chased utilisation. Time sharing adds interactive response. Short slices. A terminal user must not wait for someone else’s overnight job.

True or false. If n users share one processor in time sharing, each can feel about 1/n of the speed, ignoring OS overhead.

Yes. That is the lecture sentence. A new paper may change n. Plug in the number. Do not forget overhead if he asks “exactly 1/n?”

Short. Time sharing added extra needs. Name at least two.

Memory protection between users. Resource allocation. Mutual exclusive access to devices. Timer slices (OS10) enforce the sharing.

True or false. CTSS is a current Linux scheduler name you must configure on the Pi.

No. CTSS is the early 1960s time-sharing system on the slide (IBM 7094, up to 32 users). Lab 2 CFS/nice is OS7. Do not mix the museum name with the Pi.

11. Five achievements — a map, not the later chapters

Stallings names five major achievements in OS history. This lecture lists them. Later pages own the details. On the oral, if he says “name the big five,” you list. If he says “explain a mutex,” you go to OS3, not this list.

  1. Processes — OS1.
  2. Memory management — virtual memory, protection. Doors on OS10 (virtual vs RAM) and later lectures.
  3. Information protection and security — modes, file access, system access from rooms 3–4.
  4. Scheduling and resource management — slices, allocation, exclusive devices. Deadlock is OS5.
  5. System structure — how the OS is built (layers, later: microkernel extra switches on the exam hall).

Vista vs Apollo, and “Linux worth a billion euro,” are colour on the slide. Do not treat them as exam facts. The five names are.

Short. Name at least four of Stallings’ major OS achievements from this lecture.

Processes. Memory management. Information protection and security. Scheduling and resource management. System structure. Four of five is enough. “Chrome” is not on the list.

Twist

True or false. If you can recite the five names, you already know mutex, fork, and deadlock for 100/100.

No. This page classifies the map. Process details OS1. Mutex OS3. Deadlock OS5. He may ask a new sentence inside one of those rooms.

Written exam — this family

Same topic as the rooms. Try first. Then open the answer. A new paper can change the story (overnight tape, 30 terminals, a USB that did not exist at purchase). Map it to an aim, a service, or a history step.

Lecture 04 shape · three aims (short list)

Name the three OS objectives. One sentence each.

Answer and steps
  1. Convenience. Programs use named files and simple read/write. They do not talk to the disk chip.
  2. Efficiency. CPU, memory and devices are shared. One guest must not waste the whole machine.
  3. Ability to evolve. You can add, test and ship a new function without stopping the rest. New hardware, new services, and fixes are the three evolve stories.
  4. A new wording may say “easy to use / use resources well / grow without breaking service.” Same three.

Lecture 04 shape · services

Name OS services a written short can ask. Give four, with one line each.

Answer and steps
  1. Program development — editors, debuggers (utilities, not the kernel).
  2. Program execution — start, suspend, schedule, stop.
  3. I/O — uniform read/write. Device details hidden.
  4. Files — layout hidden; who may open is checked.
  5. System access — who may use the machine / this printer.
  6. Errors — HW (memory, device) and SW (divide by zero, bad address). React in a way that matches the error.
  7. Accounting — count usage, watch performance. Billing is one use, not the only use.

Lecture 04 shape · odd manager

The OS manages the CPU, but it is also a program on that CPU. How can it ever get control back?

Answer and steps
  1. The OS is software. There is no second processor watching from outside.
  2. It often gives the CPU to a user program (relinquishes control).
  3. It gets the keys back by a timer interrupt, an I/O interrupt, or a trap / system call.
  4. Hardware detail of save-PC-then-ISR is OS10. Here you must say why that doorbell exists.

Lecture 04 shape · serial → batch → multiprogramming → time sharing

What problem did each step kill? What did it still leave? A written paper can ask this as four short boxes.

Answer and steps
  1. Serial (no OS). Humans own a slot. Two wastes: scheduling (job early or late) and setup (mount compiler, tapes, cards). Nothing automatic.
  2. Simple batch. A monitor runs a queue. Job ends, branch back, next job. Kills setup waste. Still idle while that one job waits for I/O. Lessons: memory protection, timer/timeout, user vs monitor modes.
  3. Multiprogramming. Several programs in RAM. When A waits for disk, run B. Goal: CPU utilisation. Needs enough memory, protection, a scheduler.
  4. Time sharing. Terminals. Goal is now also response, not only utilisation. Short slices. About 1/n speed for n users, ignore OS overhead. Extra: protect users from each other, allocate resources, exclusive devices. Early name on the slide: CTSS.
  5. One core: concurrent means lives overlap, not “same instant.” Parallel same-instant needs more cores.

SS2018 written 3.7.2018 · Task 7 item 3

True or false: multithreading is useless on systems with only one processor.

Answer and steps
  1. False.
  2. One core can still overlap: thread A waits for I/O, thread B runs.
  3. That is the same reason multiprogramming was invented. Do not need two sockets.

Westerkamp SS2021 · Task 12 · 5 points · Cooperative multitasking

Explain cooperative multitasking. One advantage. One disadvantage.

Answer and steps
  1. Meaning. A task gives up the CPU itself (yield or a blocking wait). The OS does not forcibly preempt.
  2. Advantage. Lower overhead. Simpler: a task runs until it yields, so some mid-instruction races cannot happen. (Classic Mac OS, Windows 3.1.)
  3. Disadvantage. One greedy or buggy task that never yields hangs everyone. No timer can take the CPU back.
  4. Time sharing on a laptop is the opposite idea: the timer interrupt (OS10) forces a slice. That is why lecture 04 needed timeouts already at simple batch.

Later Gräßner Y/N · this family (also Floor 4)

Microkernel extra switches, can be slower? Concurrent jobs always run at the same instant? A process is an instance of a running program?

Answer and steps
  1. Microkernel slower: Y often. Drivers live in user space. Each ask is extra IPC / extra switches. That is Stallings “system structure,” not “the desktop is the OS.”
  2. Concurrent = same instant: N. Concurrent = lives overlap. On one core they take turns. Parallel = same instant.
  3. Process = running instance: Y. File on disk = program. Running copy with its own memory = process. Two Word windows: still one program file. Fork detail is OS1.

Lecture 04 · Stallings five names

Name the major OS achievements listed on the overview slide.

Answer and steps
  1. Processes — OS12. Shop door: OS1.
  2. Memory management.
  3. Information protection and security.
  4. Scheduling and resource management — deadlock is OS5.
  5. System structure (how the OS is built).
  6. If he asks “explain a mutex,” do not stay on this list. Go to OS3. Vista vs Apollo is colour on the slide, not an exam fact.
