Python Concurrency Lab

When a morning report is slow, start by asking what the program spends its time doing. Counting primes keeps Python busy calculating. A service check usually spends time waiting for a response. You’ll use a small version of each workload so you can focus on the Python.

What you observeWhat to tryWhat to check
Repeated calculations use CPUUse sequential code as a baseline, then try a process poolCompare the same work and include startup time
Independent calls spend time waitingUse a bounded thread pool with a blocking clientCheck per-call timeouts and service limits
Workers disagree about a shared totalAggregate results in the caller or protect a shared update with a lockAssert the total and keep the shared update small

Concurrency means several jobs can be in progress. Parallelism means jobs are executing at the same instant. Processes have separate memory by default. Threads in one process share memory. In a typical CPython build with the GIL enabled, threads can overlap blocking waits, but pure Python CPU work generally calls for processes if you need parallel execution.

Put concurrency_lab.py and test_concurrency_lab.py in one folder. Run them as files so spawned workers can import the module. On Windows, replace python3 in the terminal commands with py -3. Python 3.11 or newer is enough, and the lab uses only the standard library. The excerpts below come from the downloaded script. Run that full file so the imports, helper functions and main guard are available.

python3 concurrency_lab.py

Multiprocessing. Count the same work twice

Start with one function and a known answer. A prime is a whole number greater than 1 with no divisors other than 1 and itself. Try guessing the count for count_primes(2, 11) before running the tests.

def is_prime(number):
    if number < 2:
        return False
    return all(number % divisor != 0 for divisor in range(2, isqrt(number) + 1))


def count_primes(start, stop):
    return sum(is_prime(number) for number in range(start, stop))
  1. The first if rules out values below 2.
  2. isqrt(number) gives the whole-number square root. Checking possible divisors up to that number is enough. A factor above the square root would have a partner below it.
  3. Each prime contributes True, which counts as 1 in sum(). range(start, stop) excludes stop, so the sample counts 2, 3, 5 and 7.

Next, run that calculation in one child process. The child sends the number back through a queue.

def send_count(start, stop, results):
    # Send a value to the parent because the processes have separate memory.
    results.put(count_primes(start, stop))


def one_process_count(start, stop):
    ctx = mp.get_context("spawn")
    results = ctx.Queue()
    worker = ctx.Process(target=send_count, args=(start, stop, results))
    try:
        worker.start()
        try:
            # Read before joining. The worker may be waiting for space in the pipe.
            result = results.get(timeout=10)
        except Empty as error:
            raise TimeoutError("The worker did not send a result.") from error

        worker.join(timeout=10)
        if worker.exitcode != 0:
            raise RuntimeError(f"Worker did not exit cleanly: {worker.exitcode}")
        return result
    finally:
        if worker.pid is not None and worker.is_alive():
            worker.kill()
            worker.join()
        worker.close()
        results.close()
  1. get_context("spawn") selects the start method that launches a fresh interpreter when the process starts. The worker function is defined at module level so the child can find it. The __main__ guard in the downloaded file keeps a worker import from starting new workers.
  2. Queue() provides a channel. Process() describes what to run and start() launches it. send_count() uses put() to send the return value to the parent.
  3. get(timeout=10) reads the expected result or raises Empty when the wait expires. Read before joining. With a large buffered result, the child may need the parent to read the queue before the child can finish.
  4. join(timeout=10) waits for the child. Check exitcode afterward because join() also returns when its wait expires. In this example the queue belongs to this one job, so cleanup can stop an unfinished worker and discard the queue.

Job incident. An image batch hangs after workers start returning larger results. Check whether the parent joins them before reading the queue. Verify the receive order and surface a missing result as a failure. Replacing a missing result with zero would make the batch report misleading.

Both the sequential run and the one-process run return 1229 for the integers from 2 up to 9999.

Try changing the stop to 11 in both calls. You should get 4 each time. Restore the bounds before comparing the pool.

Process pool. Reuse workers across batches

Now split that same workload into (2, 5000) and (5000, 10000). The first range stops before 5000, so the second starts exactly where the first leaves off.

def pooled_counts(ranges):
    # Reuse two workers and keep the counts in the order the jobs were submitted.
    with ProcessPoolExecutor(max_workers=2, mp_context=mp.get_context("spawn")) as pool:
        futures = [pool.submit(count_primes, start, stop) for start, stop in ranges]
        return [future.result() for future in futures]
  1. The with block creates an executor that can run at most two worker processes at once. It waits for pending work at shutdown.
  2. Each submit() hands one range to the pool and gives you back a Future representing the job.
  3. After submitting every job, the list gets each result() in submission order. It waits when a result is still pending and re-raises any worker exception.
Process pool: [669, 560] Total: 1229

Job incident. A large reporting job pegs one core. Try partitioning independent records, returning a compact result from each batch and combining them in the parent. Compare elapsed time with the sequential run. For tiny batches, sending data and starting processes may cost more than the work itself.

Thread pool. Keep the result tied to the service

Imagine a dashboard checking CRM, Payments and Inventory. Here sleep() simulates I/O waiting and Payments raises OSError so you can practice the failure path without any network calls.

def check_service(name):
    sleep(0.02)  # Simulated I/O wait. No network request is made.
    if name == "Payments":
        raise OSError("service unavailable")
    return "healthy"


def ordered_checks(names):
    with ThreadPoolExecutor(max_workers=2) as pool:
        return list(pool.map(check_service, names))

map() yields results in input order. An early slow service can delay the display of later results even if those calls have already finished. To handle each finished job independently, keep a lookup from each future to the service that created it.

def service_report(names):
    report = {}
    with ThreadPoolExecutor(max_workers=2) as pool:
        jobs = {pool.submit(check_service, name): name for name in names}
        for future in as_completed(jobs):
            name = jobs[future]
            try:
                report[name] = future.result()
            except OSError as error:
                report[name] = str(error)
    return report
  1. submit() loops through the services and stores each future as a dictionary key. Its value is the service name.
  2. as_completed() yields the finished futures. Use the dictionary to recover the name before reading the result. Jobs that finish together have no useful ordering guarantee.
  3. result() returns a healthy status or raises the worker’s exception. Here the handler records the expected service failure and lets the other jobs report their results.
CRM: healthy
Inventory: healthy
Payments: service unavailable

The demo sorts the final report to give you stable console output. For live progress, handle or display the result inside the as_completed() loop.

Job incident. A monitoring page freezes when one connection stalls. Keep a worker limit and set a timeout on the actual network call. future.result(timeout=...) only limits how long the caller waits for the future. It doesn’t stop work that’s already running.

Reproduce a lost update and fix it

Two threads each add one to the same total. The barrier is a teaching aid. It makes both threads read zero before either writes, so you can reproduce the lost update without guessing thread timing.

def count_completed_checks(protect_update):
    total = 0
    both_have_read = Barrier(2)
    lock = Lock()

    def update():
        nonlocal total
        if protect_update:
            with lock:
                total += 1
        else:
            before = total
            # Force both threads to read 0 before either writes.
            both_have_read.wait(timeout=5)
            total = before + 1

    with ThreadPoolExecutor(max_workers=2) as pool:
        jobs = [pool.submit(update) for _ in range(2)]
        for job in jobs:
            job.result()
    return total

Without protection, both workers write 1. With with lock:, each worker finishes its read, add and write before the other enters. The result is 2. The barrier is only used in the unprotected branch. Waiting at a barrier while holding the lock would prevent the second worker from reaching it.

Testing. Assert outcomes you can rely on

Run the tests from the same folder as the lab. The test file imports the functions. The main guard keeps the demonstration from running at import time.

python3 -m unittest -v test_concurrency_lab

The suite should report Ran 7 tests and OK. Read these two tests first. The first compares the pool against a known result and the sequential implementation. The second checks that a failed worker still has a finished future and its exception reaches the caller.

def test_pool_matches_sequential_count(self):
        ranges = [(2, 5000), (5000, 10000)]
        counts = pooled_counts(ranges)
        self.assertEqual(counts, [669, 560])
        self.assertEqual(sum(counts), count_primes(2, 10000))
def test_future_propagates_worker_error(self):
        with ThreadPoolExecutor(max_workers=1) as pool:
            future = pool.submit(check_service, "Payments")
            with self.assertRaisesRegex(OSError, "service unavailable"):
                future.result()
            self.assertTrue(future.done())
  • assertEqual(counts, [669, 560]) checks the counts for both ranges. Comparing with the sequential count checks that the split covers the same input.
  • assertRaisesRegex() checks the exception type and message. That tells you the failure was recorded for the expected reason.
  • assertTrue(future.done()) proves that completion alone can include failure. Other tests check ordered results, label association and the shared counter.

Work scenarios and interview checks

SituationFirst response
PDF conversion saturates CPUMeasure a single document first, then try a small process pool across independent documents. Check memory and avoid sending full document contents when workers can open their own files.
Partner API starts returning 429Reduce the request rate and follow the provider’s retry instructions. A thread pool limits workers, but a worker limit alone does not guarantee a request rate.
One failed lookup hides successful resultsTrack a future per lookup and record failures alongside successes. Test each result against its own input label.
Why not call result() directly after every submit()?

Waiting immediately serializes this loop. Submit the independent jobs first, then collect results.

Can future.done() be true after cancellation?

Yes. A future can be done after returning a value, raising an exception or being cancelled.

Why does the process pool need a top-level function?

Spawned workers import the module. Use a function they can import and inputs and outputs that can be serialized.

Does the GIL prevent lost updates?

No. Several steps can form one logical update. Use a lock around the whole update or aggregate in one thread.

What changes if you use await with a blocking library?

A blocking call still blocks the event-loop thread if you run it directly there. Use an async client or move the blocking call off that thread.

Why might adding processes slow the job down?

Startup, serialization and scheduling all cost time. Small tasks may spend more time on those costs than on the calculation.
