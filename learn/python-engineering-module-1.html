Abstract

Learning purpose

This module introduces Python through realistic engineering problems, from expense analysis to data validation and asynchronous service calls. Each chapter includes ordered subtopics, a runnable example, independent practice, progressive hints and a reference solution.

Outcomes: write modular programs, choose suitable data structures, process files safely, model domain objects, use type hints, test edge cases and explain basic concurrency.

Learning method: predict → run → modify → solve → explain. Work through the challenge before opening the solution. Estimated times are flexible and do not replace demonstrated competence.

Prerequisites: basic computer literacy. Next modules: Git and Linux, SQL, OS and networking, DSA, testing and backend development.

Industry practice · Project 01

Transaction Tracker CLI

Business brief: Build a command-line application for importing and reporting expenses. Operations teams need accurate totals, traceable rejections and reproducible results.

Acceptance criteria

  1. Read CSV containing transaction ID, date, category and amount.
  2. Use Decimal for currency, rejecting negative or non-finite amounts.
  3. Detect duplicate transaction IDs and report rejected rows with reasons.
  4. Generate totals by category and a grand total.
  5. Export a JSON report and provide a useful CLI summary.
  6. Separate parsing, validation, calculations and presentation.
  7. Write pytest tests for normal, empty, duplicate and malformed inputs.
  8. Provide a README, setup instructions and sample commands.

Suggested file structure

transaction-tracker/
├── README.md
├── pyproject.toml
├── src/transaction_tracker/
│   ├── cli.py
│   ├── models.py
│   ├── importers.py
│   └── reports.py
├── tests/
│   ├── test_importers.py
│   └── test_reports.py
└── examples/transactions.csv

Project stages

A. Parse five sample records. B. Add validation and duplicate detection. C. Generate accurate reports. D. Add tests and document a complete demonstration.

Architecture hint

Keep parsing and validation separate from aggregation. Design the aggregation function so it can be tested without opening files.

Reference design
CSV → parser → validator → validated records
                   ↓                 ↓
             rejected rows      aggregation
                                     ↓
                               CLI + JSON report
